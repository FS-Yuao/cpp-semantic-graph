## 1 引言

### 1.1 目的

描述当前 AI 工作环境（harness）的优化方案现状：总体架构、记忆子系统三路机制（注入/检索/沉淀）的设计实现、与 2026 年市场主流记忆技术的对标结论、客观现状评估与分级优化路线。作为后续 harness 迭代决策的基准文档。

### 1.2 范围

覆盖单用户（单人开发）单领域（ADC4.0 OTA 项目 + 配套基础设施工程）场景下的完整 harness：宿主客户端、模型、规则人格层、记忆知识层、角色外脑层、流程协议层、自动化层、观测治理层。不覆盖多用户/多租户场景（见 §7 约束）。

### 1.3 术语定义

| 术语 | 定义 |
|---|---|
| harness | 承载 AI 模型完成工程任务的完整工作环境：宿主框架 + 规则 + 工具 + 记忆 + 流程协议的总和 |
| doc-graph | 文档知识图谱服务（HTTP 单例 :8930），存文档节点/知识点/finding 经验库 |
| cppsg | C++ 代码语义图谱（semantic_graph_full.db），覆盖 ap-aa/app 业务模块 170 TU |
| finding | 经验结论条目（fact/constraint/decision/lesson/risk 五型），带符号锚定与证据计数 |
| 注入路/检索路/沉淀路 | 记忆子系统的三条路径：会话开始强制注入、按需检索、会话收尾沉淀 |
| freshness | finding 时效检测机制：锚定符号在代码库中是否仍存在 |

## 2 总体描述

### 2.1 系统定位

harness 的设计目标：让 AI 在长期、连续的工程任务中保持正确的决策质量——记住历史结论、遵守已定约束、不重蹈覆辙、不重复推导。核心思路是**分层记忆 + 机制化回忆 + 证据化沉淀**，替代默认的"每会话从零开始"。

### 2.2 总体架构（六层）

```
┌────────────────────────────────────────────────────────┐
│ 宿主：CodeBuddy(QBuddy) IDE —— agent 循环/工具协议/     │
│       hooks 生命周期(27+ 事件)/Task 子代理/团队模式      │
│ 模型：GLM（主 agent 与子代理共用）                      │
├────────────────────────────────────────────────────────┤
│ L1 规则人格层（每次会话注入的行为基准）                  │
│    通用规则(四要素人格) → 项目规则(事实红线) → 21 skills │
├────────────────────────────────────────────────────────┤
│ L2 记忆知识层（三路）                                    │
│    注入路：SessionStart hook → MAP(12KB)+RECENT(8KB)    │
│            +常驻答案页(3KB)，三级硬预算                  │
│    检索路：doc-graph(findings 118+文档 267 节点)         │
│            cppsg(代码图谱)+clangd(SDK/BSW 兜底)          │
│    沉淀路：record_finding 幂等写入/回写五步协议/         │
│            每日记忆/constraint_index/bugs 总账           │
├────────────────────────────────────────────────────────┤
│ L3 角色外脑层：architect-anchor(锚定)/reviewer(审查)/    │
│    bug-analyst(日志包分析)/code-explorer + 并行只读消化  │
├────────────────────────────────────────────────────────┤
│ L4 流程协议层：入口锚定→文档先行→测试先行→编码→验证审查  │
│    session-handoff(会话交接)/daily-summary/dev-loop      │
├────────────────────────────────────────────────────────┤
│ L5 自动化层：cron×4(记忆入库/图谱增量/RECENT 再生/       │
│    纪律审计)；hooks×3(SessionStart/PreToolUse 守卫/      │
│    PostToolUse dirty 标记)                              │
├────────────────────────────────────────────────────────┤
│ L6 观测治理层：search-stats 体检/每日纪律审计/           │
│    双遥测 jsonl/finding 生命周期/迁移资产四层模型        │
└────────────────────────────────────────────────────────┘
```

### 2.3 运行环境

- 宿主：CodeBuddy IDE（QBuddy），兼容 Claude Code hooks 规范
- 模型：GLM 系列经宿主接入
- 基础设施：doc-graph MCP（systemd user unit，HTTP :8930 单例）、cppsg（SQLite，cron 21:40 增量）、clangd LSP（compile_commands 全项目范围）
- 知识资产冷备：GitHub 私有仓库 FS-Yuao/adc4-knowledge-docs（配置快照/记忆冷备份/基础设施源码三层）

### 2.4 设计约束

- 单用户单领域：无多租户隔离需求，无跨用户记忆共享需求
- 全本地优先：知识资产不依赖云服务（向量模型曾评估后否决，见 §5.4）
- 上下文预算刚性：注入总量硬上限约 23KB，超限即截断（当前 MAP 已超限 17%）

## 4 记忆子系统结构

### 4.1 写入（沉淀路）

```
会话/分析产出结论
      │
      ▼
record_finding_tool（MCP，写入 doc_graph.db）
      ├─ 同 title 幂等合并（v2 增量追加模式）
      ├─ 符号锚定（finding_symbol 表，118/118 全锚定）
      ├─ 证据计数 evidence_count + last_confirmed
      └─ FTS5 索引 + 向量 embedding（fastembed bge-small-zh，可选降级）
      │
      ▼
配套沉淀：每日记忆(YYYY-MM-DD.md，锚点追加式) / constraint_index
         四元组 / PROJECT_MAP 目录行 / bugs 总账 / 任务三件套
```

写入触发靠**流程协议纪律**（回写五步、reviewer 第四阶段核验），非自动抽取。写入内容带行号级证据坐标（日志文件名+行号 / 代码文件名+行号），推测强制标注 suspected。

### 4.2 召回（注入路 + 检索路）

注入路（高频，零检索成本）：会话开始 hook 注入三级内容——PROJECT_MAP（长期目录）、RECENT（14 天窗口）、STANDING_ANSWERS（高频架构事实预计算答案，只收带行号证据条目）。

检索路（低频深查，渐进披露两步式）：`doc_graph_search` 默认返回目录级（文档 title/path/一句话摘要 100 字符截断、知识点标题索引带行号、符号名列表截 30、findings 精简为 id/title/状态/置信度，cppsg 桥接不展开）；调用方判断相关后带 `include_detail=true` 重查同关键词取全量。实测同关键词（"串口让渡"）单次返回 79153B → 10215B（13%）。代码类查询走 cppsg 三场景工具，降级链 cppsg → clangd → 文本检索。

### 4.3 生命周期治理

- freshness 三层判定（2026-10-22）：域外注册表豁免（MCU 日志/芯片标识）→ cppsg 存在性精查 → 仓库级 grep 兜底（BSW/SDK/工具链检索根），原则"宁漏标不误标"
- 衰减排序：evidence_count 加成 + last_confirmed 180 天线性衰减，刹车"库自我污染"
- 幂等恢复：stale → active 自动迁移，恢复计一次证据

## 5 市场主流技术对标

### 5.1 主流记忆写入技术（2026 年格局）

| 阵营 | 代表 | 写入机制 | 核心特征 |
|---|---|---|---|
| 异步巩固派 | ChatGPT Dreaming V3 | 后台进程空闲时自动整理：陈旧性检测、冲突消解、规模化降本（约 1/5） | 异步冷路径，系统主导 |
| 文件派 | Claude memory tool / Claude Code Auto Memory | 模型自主调文件操作工具写 /memories 目录；Auto Memory 自动写 MEMORY.md | 像管理代码库一样管理记忆，Git 可审计 |
| OS 范式 | Letta/MemGPT | Agent 经 function call 自编辑记忆块（core_memory_replace）；sleep-time agents 空闲重放整理 | 最早的"自管理记忆"工程实现 |
| 抽取管道 | Mem0 | 两阶段：小模型抽取候选事实 → LLM 对比库内做 ADD/UPDATE/DELETE/NOOP 决策 | 轻量增量维护，LOCOMO 单跳 +42%/token -94% |
| 时序图谱 | Zep/Graphiti | 双时态（事件时间/摄取时间）知识图谱；矛盾时旧边打 t_invalid（逻辑失效非物理删除） | 支持时间旅行查询，增量构建 |
| 双路径 | LangMem | Hot path 会话中同步抽取 + Background Reflection 会话后反思 | 语义/情景/程序性三分，程序性=动态改写系统提示词 |
| 三形态 | MemOS（学术） | MemCube 统一明文/激活（KV Cache）/参数（LoRA）三形态可互转 | 前沿探索 |
| 上下文工程 | Manus | 不建记忆库：append-only 追加、掩码遮蔽式"遗忘"、状态外置文件 | KV-Cache 命中率优先，适合小时级单任务 |

### 5.2 主流记忆召回技术

三分类：**全量注入**（记忆摘要拼进系统提示）→ **按需召回**（向量/图遍历/混合检索 + 重排）→ **渐进披露**（目录常驻、正文按需）。渐进披露以 Claude 生产系统提示词为代表：先读记忆目录（仅标题+一句话描述）→ 判断相关性 → 相关才加载正文。混合检索以 Zep 为代表：语义 + BM25 + 图遍历三路并行，RRF 融合 + rerank。

### 5.3 安全与评测

记忆投毒（恶意内容持久化驻留）公开研究攻击成功率 80%+，OWASP Agentic Top 10 列为 ASI06；文件系统类记忆天然具备版本化回滚审计能力。评测基准：LOCOMO、LongMemEval、DMR、AMB。

### 5.4 本方案坐标定位

| 维度 | 市场主流 | 本方案 | 差距/优势 |
|---|---|---|---|
| 写入触发 | 自动抽取（Mem0/LangMem）或模型自主（Claude） | 流程纪律触发 + 行号级证据坐标 | **优势**：证据质量远超通用抽取管线（单领域深耕红利）；**差距**：依赖纪律自觉，无自动抽取兜底 |
| 写入决策 | ADD/UPDATE/DELETE/NOOP 四操作框架 | 同 title 幂等合并（LLM 判断追加） | 雏形具备，无显式 DELETE/矛盾消解框架（BUG-025 risk finding 曾被误覆盖，靠 evidence_count 发现） |
| 冲突消解 | Zep edge invalidation / Dreaming 冲突合并 | 无 | 差距（单用户场景矛盾频率低，代价可承受） |
| 时间模型 | bi-temporal 双时态 | updated_at 单时间戳 | 差距（无"过去何时成立"查询需求，暂不需要） |
| 召回策略 | 渐进披露（Claude 模式） | 注入蒸馏（三级预算）+ 检索两步渐进（2026-10-23 O-1 落地，返回体积 13%） | **已对齐**：注入路目录式 + 检索路目录级/详情两步，同 Claude 渐进披露模式 |
| 时效自净 | Dreaming 陈旧性检测 / Zep 边失效 | freshness 三层判定（符号存在性） | 部分：只检测"符号消失"型，检测不了"语义漂移"型（BUG-008 机制漂移案例靠人工抽查发现） |
| 证据模型 | Hindsight observations（计数+确认时间） | evidence_count/last_confirmed（同源借鉴） | 机制对齐；2026-10-23 存量回填后零值 0%，衰减排序全量生效 |
| 代码锚定 | 通用框架均不做 | doc↔code 符号桥接 + clangd 全项目 | **优势**：市场记忆框架几乎无代码语义级锚定 |
| 治理观测 | 多数框架缺失 | 双遥测/审计/消费度检测/体检 | **优势**：工程化程度深 |
| 向量召回 | 标配 | 已实测否决（bge-m3 重评 margin -0.048 不通过，三量级 encoder 全败） | 明知故不做：短查询 vs 短结论的语义判别非 encoder 量级问题，维持"调用侧改写+同义表+排序增强" |

### 5.5 结论

不引入外部记忆框架（Mem0/Zep/Letta）：单用户单领域深耕场景下，本方案的行号级证据锚定、代码图谱融合、治理观测层是通用框架不具备的；通用抽取管线反而会稀释证据质量。**该吸收的是模式不是框架**：渐进披露（Claude 已验证）、异步巩固（Dreaming/Letta，基础设施就绪但触发条件未到）、四操作写入决策（已有雏形）。

## 6 现状评估与优化路线

### 6.1 客观评价

**优势**（均有实证）：沉淀闭环有效——写读比 1.4（80 写/57 读，2026-09-22 起遥测），findings 118 条全符号锚定，证据坐标纪律执行到位（BUG-025 条目行号级证据密集）；cppsg 影响面查询零失败（callers 42 次居首）；freshness 三层判定修复后误标归零。

**短板**（按杠杆大小排序，1 已解决）：

1. ~~召回侧在浪费写入侧攒下的资产~~（**2026-10-23 已解决**：O-1/O-2/O-3 落地——渐进披露返回体积 13%、parser 穿透修复、evidence 全量回填，见 §6.2 实施结果）。
2. **热路径阻塞**：record_finding 均耗 2.9s（遥测 80 次），违背"热路径只做缓冲、重活异步下沉"的行业共识；embedding 推理为首要嫌疑（待 profile 实证）。
3. **时效检测盲区**：语义漂移型过时（代码在、行为变）结构上检测不到。
4. **注入预算饱和**：MAP 超限截断 17%（14022B/12000B），预算管理靠蒸馏维护。
5. **宿主机制坑**：spawn 必须显式 mode=bypassPermissions（靠 PreToolUse 守卫强制补丁）；UserPromptSubmit stdout 不注入（通道半残）；IDE automations 调度引擎不稳定。

### 6.3 决策建议

1. 自研路线维持，不换框架（依据 §5.5）。
2. 资源优先投召回侧（O-1/O-2/O-3 打包一批，半天量级）——写入侧资产已厚，召回是当前瓶颈。
3. P2 三项全部挂起但写明重评触发条件，防止无限期搁置变成永久遗忘。
